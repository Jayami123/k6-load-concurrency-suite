Scope reminder. All targets are Jayami's own locally hosted forks (Cal.com, Documenso, Medusa, Twenty) in Docker. Security content stays at QA test-design level (expected status codes, headers, scanner config). No exploit payloads. Ideation metrics are targets to measure, not claims.

1. Goal & what this showcases

Show that Jayami can prove correctness under contention and then measure performance without vanity numbers. The ideation brief asks for race tests plus k6 smoke/ramp/stress/spike with thresholds (error rate, p95, p99), think time, dynamic auth and an HTML dashboard. Ideation-chat figures like "p95<200ms at 2000 RPS" are targets to measure, never README claims. Every race uses a DB/API oracle; every k6 scenario writes a baseline artefact before any threshold is enforced.

  • Race matrix with statistical trials (N≥50) and status histograms — not a single lucky pass.
  • k6 scenarios (smoke → ramp → stress → spike) with think time, dynamic auth tokens, and thresholds that start as thresholds: {} until a baseline run fills them.
  • Cross-product contention themes: Cal booking slots, Medusa stock/money, Documenso signing completion, Twenty lost-updates and token races.
  • HTML k6 dashboard (k6 report or xk6 dashboard) published as a CI artefact.

Documenso

  • Same as P2. Race: last two recipients complete in parallel; double-submit of one recipient.
  • Oracle: sealed PDF count, BackgroundJob seal jobs, WebhookCall DOCUMENT_COMPLETED count, Inbucket completed emails.

Medusa

  • Pinned app + Redis locking module. Stock S; N carts.
  • Multi-instance: two medusa develop (or containers) behind distinct ports; same DB/Redis.
  • Oracle: order count, reservation_item sum, inventory quantity.

Twenty

  • Image 2.44.0. Race: two API patches on same record; concurrent reset redemption (shared with P5).
  • Oracle: final field value via REST; password hash updated once.

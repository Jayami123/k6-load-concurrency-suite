## 2. What it proves

There is no mapped case ID. The task proves two things about the weekly soak, which is a measurement and not a gate.

- **Capture (no verdict, only evidence).** Every weekly 2 h scheduled soak run either leaves one token-scanned summary per product in a `p6-soak-<yyyy>-w<ww>` release, or leaves a visible gap for that week with the reason. A week with no release at all is shown as a gap too, so no week is silently dropped. Question: does each week's soak leave a comparable record? Oracle: the summary schema v1 (section 6.4) and the validity rule (section 7). Verdict words for the capture job: **PUBLISHED** (release created, every product file present), **PUBLISHED WITH GAPS** (release created, one or more products are INVALID or missing, each with its reason), **REFUSED** (the week's tag or draft already exists, or a validation step failed; nothing is changed), **NOT RUN** (the run is not a weekly point, for example a nightly 30-min run, or the soak failed before any upload).
- **Trend view (measure only, no threshold).** The dashboard shows, per product, the weekly RSS, fds and DB-connection slopes and plateau ratios, plus a health-probe latency proxy, with a link to each week's run. Every point prints its soak verdict beside it, so a trend is never read as a pass. Question: does slow degradation show across weeks? Oracle: the pure trend function (section 6.7) on fixtures. Verdict words for the view: **collecting (n/3 weeks)** (fewer than 3 VALID points for the product), **trend** (3 or more VALID points: the chart is drawn). There is no PASS or FAIL in the trend. The roadmap says "No trend threshold or gate (measure-only)" (line 482).

Transfer: a payments platform or an EHR interface team watches the slow drift between upgrades. The view answers "is the memory of the service creeping over weeks?" without a gate.

### 6.2 Modules and data flow

```
soak run (schedule, 120 min, completes with success or failure)
   │  artefacts soak-<product>-120 (90 days; none if the run failed before upload)
   ▼  workflow_run (soak-release, branches: [main])
decide job  ── fetch run, artefacts and jobs (gh api) → ancestor check (head_sha on origin/main)
   │          → weeklyDecision (trigger mode: NOT RUN exit 0; dispatch mode: refuse exit 1)
   │          → outputs: weekly, run_id, tag, head_sha, created_at, iso_week, products
   │ weekly=true
   ▼
capture job (concurrency soak-release-<tag>)
   │  refuse existing tag or draft (REFUSED exit 0)
   │  → gh run download (soak-*-120) → keep allowlisted files → token scan → gitleaks (raw)
   │  → summarize (soak.json, run-meta.json, telemetry, job results) → one file per product
   │  → token scan + gitleaks (summaries) → upload artefact "weekly-summaries" (1 day)
   ▼
publish job (concurrency soak-release-<tag>)
   │  download "weekly-summaries" → refuse existing tag or draft → token scan + gitleaks (again)
   │  → gh release create --draft --target <head_sha> --latest=false → upload assets
   │  → verify assets against SHA256SUMS.txt → gh release edit --draft=false --latest=false
   ▼
pages.yml (workflow_run of soak-release completed, branch main, success)
   ├─ soak-summaries job: list releases (paginate), keep p6-soak-*, download assets and sums,
   │     check sha256, write release.json per tag, token scan + gitleaks, upload artefact "soak-weekly"
   └─ build job (needs soak-summaries): build-site.ts --weekly-soak <dir>
         → src/dashboard/soak/weekly-trend.ts (pure, gap-fill to expectedThrough)
         → src/dashboard/render/weekly-soak.ts → site/index.html (section "Weekly soak trend")
         → scan job (unchanged) → deploy (unchanged)
```

`weeklyIsoWeek` skeleton:

```ts
export function weeklyIsoWeek(createdAtIso: string): { isoWeek: string; tag: string } {
  const created = Date.parse(createdAtIso);
  if (Number.isNaN(created)) throw new Error(`weekly: created_at is not a date: ${createdAtIso}`);
  // Sunday 19:29 UTC minus 6 days 19 h 29 min is Monday 00:00 UTC of the same week.
  const shifted = new Date(created - (6 * 24 + 19) * 3600e3 - 29 * 60e3);
  return { isoWeek: isoWeekOf(shifted), tag: `p6-soak-${isoWeekOf(shifted)}` }; // isoWeekOf: Thursday method, "YYYY-wWW"
}
```

1. **Incomplete release.** If `draft` is true, or `sums` is null, or a name in `sums` is missing from `assets`: every product gets a gap for that release with reason `incomplete release`. The files of that release are ignored.

4. **Invalid summary.** `valid` false → gap with `summary.invalidReason`.

### 6.11 Oracles and verdict rules

- **Validity** (`valid`): D-T7-5. The verdict values come from src/load/soak/verdict.ts lines 4–12.
- **Weekly point**: D-T7-2, rules 1–7 of `weeklyDecision` (section 6.6).
- **Week**: D-T7-3, `weeklyIsoWeek(created_at)`.
- **Status**: `n` = the count of VALID points of one product; `statusFor(n)` = `collecting (${n}/3 weeks)` when `n < 3`, otherwise `trend`. The number 3 is `REQUIRED_VALID_WEEKS` only.
- **Gap-fill**: D-T7-14, rule 8 of `buildWeeklyTrend`: weeks from the first release to `expectedThrough` with no release.
- **Markers**: a change of `productSha`, `harnessTag` or `k6Version` between consecutive VALID points. Gaps do not break the chain.
- **No threshold**: nothing in this view is a PASS or FAIL. The soak's own verdict is printed beside every point as text and never turned into a colour rule. (The roadmap says measure-only, line 482.)
- **Units**: slopes in MB per minute (RSS), fds per minute, connections per minute; plateau ratio is the last third over the middle third (plateau.ts); probe in ms, slope in ms per minute.

### 6.12 Data isolation, cleanup and leak check

- Each capture reads only its own run's artefacts (the run id is an input). No state is shared between runs except the release tag.
- The leak check is the token scan and gitleaks that evidence-release uses. It runs **before** any upload, on the raw download after the file-type filter, and again on the summaries. A hit stops the job (exit 1). Nothing is uploaded and no draft is created.
- The gzipped points are not scanned and not published (P-45, section 14.3). This is the one place the scan does not reach, and the plan says so.
- The summary keys are restricted (section 6.4). The validator refuses forbidden keys.
- The raw artefacts are never uploaded by the capture. They are deleted with the runner.
- The allowlist of `.gitleaks.toml` is not changed (P-31).
